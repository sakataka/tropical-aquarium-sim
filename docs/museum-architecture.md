# 水の生き物館（仮称） 設計（2026年10月）

自宅のフィッシュルームから、架空の展示館へ舞台を移す。生き物の種類を数百まで増やしても、世界観と構造が破綻しないようにするための方針と、アーキテクチャの変更点をまとめる。

## なぜ展示館にするか

自宅に置ける水槽は10台程度が限度で、それを超えるとリアリティがなくなる。今後は冷たい水の魚、深海の生き物、カニなど魚以外の水の生き物まで広げたいので、「なぜここにいるのか」を場所の設定で説明できる展示館にする。

- 場所は架空でよい。生き物と水槽の中は、これまでどおりリアルに作る。
- 今の「一枚絵の部屋に5〜6水槽、寄ると水槽画面」という仕組みを、そのまま**展示室**として使う。部屋の上に**館マップ**を1段足す。
- 利用者は**館長**として、展示を眺め、水槽ごとの生き物の数・水景・照明を組む。今の設定操作をそのまま残す。
- 画面の調子はすでに「夜の自然史博物館の展示」を軸にしているので、展示館という設定と合う。

## 載せる生き物の範囲

| 対象 | 方針 |
|---|---|---|
| 家庭で飼育される魚・エビ | 今の路線 |
| 実在するが家庭では飼えない生き物（深海、冷たい海、大型種、公共水族館でしか見られない種） | 載せる |
| 魚以外の水の生き物（カニ、ヤドカリ、貝、ウニ、クラゲ、タコ、両生類など） | 載せる。体のつくりごとに動きと描画を足す |
| 水族館にいる爬虫類・哺乳類・鳥（ウミガメ、ペンギン、アザラシ、イルカ、ワニ、カワウソなど） | 載せる前提（2026年10月10日、ユーザーより）。基準は「水族館にいそうか」で、明らかに水族館にいないもの（クジラ、カバ、水鳥など）は載せない。哺乳類などは動きを作るのが難しいので、体のつくりができるまでは展示計画の候補のまま置く |
| 改良品種（金魚、メダカ、錦鯉など） | 同じ種として数える。姿の違いとして複数置いてよい（図鑑の種数は `speciesKey` で数えるので、同じ `speciesKey` を持つ別の項目にできる） |
| 絶滅種の復元 | 当面は載せない |
| 架空の生き物 | 載せない（世界観が崩れるため） |

「家庭で飼えるかどうか」は図鑑で区別して表示する（下記 `profile.keeping`）。

## 体験の構成

```
館内図（トップ）       建物の断面図。建物が複数あれば、上の切り替えで建物を選ぶ
 └ 建物                本館、海の館、川と湖の館。建物ごとに断面図と階を持つ
    └ 階（ゾーン）      ジャンルのまとまり。1階に展示室が1つ以上
       └ 展示室         一枚絵に5〜6水槽。今の「部屋」
          └ 水槽        鑑賞モードと設定モード（今と同じ）
図鑑                    全生き物の生態解説。どの水槽で見られるかから水槽へ飛べる
```

### 建物と階の構成

館は3つの建物からなる（2026年10月10日に決定）。開いているのは本館の18展示室・84水槽で、残りは計画中（館内図には「準備中」の枠で出る）。計画の全体は50展示室・254水槽で、約1,300〜1,500種を受け止める器として用意した（水槽1つに平均6〜7種で約1,600種ぶん）。水槽ごとの種・水景の説明・入れたい種の手がかりは、保管庫の `catalog/exhibit-plan.json`（展示計画。第2版）が正本。

| 建物 | 役割 |
|---|---|
| 本館（`main`） | 「身近な水辺から、遠く深い水へ」のひとめぐり。地上4階・地下2階。上へ行くほど遠い水、下へ行くほど特殊な水 |
| 海の館（`ocean`） | 世界の海を広く・深く。地上3階・地下2階。上の階ほど浅く明るい海、下の階ほど深く暗い海 |
| 川と湖の館（`freshwater`） | 世界の淡水を大陸ごとに掘り下げ、人と水辺の関わり（金魚、外来種、両生類、水生昆虫）まで見せる。地上3階 |

本館と新しい建物でテーマが重なってよい（本館はひとめぐり、新しい建物は掘り下げ）。3つに分けた理由: 1,300種を今の密度（水槽1つに4〜5種）で受けると50室前後が要り、本館の6階に足すと1階あたり8室を超える。東西の翼のように本館と同じ階のテーマを並べる案は、テーマごとに要る展示室の数が違いすぎて（海は15室以上、生きた化石は1室）、片方の翼が空く。建物ごとに階のテーマを持てる形なら、海と淡水という分かりやすい区切りで足せる。

- 第2弾（18水槽）: カニ、クラゲ、タコ、エイ、両生類などの体のつくりを足してから。済み。
- 第3弾（159水槽）: 今の体のつくりで開けられる、計画中の水槽。展示室の絵と水景ができ、種の画像と調査が届いたところから開ける。
- 第4弾（11水槽）: まだ描けない体のつくり（二枚貝、イソギンチャク、等脚類、水生昆虫、カメなど）が主役の水槽。

これまでの経過: 2026年10月5日に地上4階・地下2階、18展示室、84水槽の本館を決め、10月6日に新しい館内図と展示室の絵へ切り替えて18室を開けた（旧来の2部屋はなくし、既存の7水槽は新しい展示室へ移した）。魚以外の生き物を待つ14水槽は、体のつくりを足すごとに開け、10月9日に84水槽すべてが開いた。10月10日に建物の段を足し、海の館と川と湖の館、本館の3室（北の川とサケの遡上、琵琶湖と日本の湖、琉球の川と河口）を計画に加えた。

水族館にいそうな爬虫類・哺乳類・鳥（ウミガメ、ペンギン、アザラシ、イルカ、ワニ、カワウソなど）は載せる前提にし、37種を計画中の水槽の候補に入れた（2026年10月10日、ユーザーより。上の「載せる生き物の範囲」）。どれもまだ描けない体のつくりなので、候補には `needs` が付いている。今の水槽では小さすぎる大型の種と、置ける水槽のまだない種（温帯のペンギン、ジュゴンなど）は、展示計画の `notes.notPlannedJa` に書いた。外来種（オオクチバス、ブルーギルなど）は「外来種の水辺」だけに置き、原産地の水槽には重ねて置かない。ユーザーが決めたことは展示計画の `decisions` にも残している。

### 図鑑

生態を学べる内容にする（2026年10月に方針を変更。以前は「観察文などは足さない」としていた）。ただし、見つけた種を集める、未発見を隠す、といった収集・達成の仕組みは付けず、最初から全種を読めるようにする。世話や成績を持ち込まない方針は変えない。

## アーキテクチャの変更点

今の「`src/content/` にフォルダを置けば読み込まれ、ビルド時に zod で形と参照を検証し、`content.test.ts` で参照切れを検出する」という仕組みは、数百種でもそのまま使う。変えるのは次の7点。

### 1. 館・建物・階・展示室の階層（実装済み）

館 → 建物 → 階 → 展示室 → 水槽の順に並ぶ（建物の段は2026年10月10日に足した）。

- `src/content/museum/museum.json`: 館の名前と紹介文だけ。
- `src/content/museum/buildings/<id>/building.json`: 建物（`id`・`order`（館内図に並べる順）・名前・紹介文）、断面図の絵（`map`。同じフォルダに置く）、階の一覧（`id`・`order`（上からの並び）・「1階」「地下1階」などの表示・英字名・テーマ・断面図の中の範囲 `mapArea`）と、各階の展示室の枠（`halls`）。**建物を足すときは、このフォルダを1つ足す**（中央の一覧は書き換えない）。`order` がいちばん小さい建物（本館 `main`）を、何も指定せずに開いたときに見せる。読み込みは `src/core/museum.ts`（ビルド時に作る館の索引 `virtual:museum` を読む。`buildings`・`floors`・`getBuildingOfFloor` など）。
- **階・展示室・水槽の id は館全体で重ならない**（ビルドとテストが確かめる）。新しい建物の階は、建物名を頭に付ける（`ocean-reefs` など）。そのため、建物を足しても URL（`?floor=`・`?hall=`・`?tank=`）と保存データの形は変わらず、展示室を別の建物や階へ移しても、展示室と水槽の URL は変わらない。
- 展示室をどの建物のどの階に置くかは `building.json` の `halls` だけで決める。枠の `id` と同じ `room/*.json` があれば開いている展示室、なければ準備中で、準備中の枠には `displayName` を書く。どの枠にも置かれていない展示室はビルドで止まる。枠の並びは展示計画（保管庫の `catalog/exhibit-plan.json`）と同じにし、`bun run plan:check` で食い違いを見つける（下の「展示計画との突き合わせ」）。
- 館内図（`src/ui/MuseumMap.tsx`）は2段。1段目は、建物の断面図（画像生成した絵）に階の帯を重ねたものと、横（狭い画面では下）のフロアガイドで、階を選ぶ。建物が複数あるときは、見出しの下に建物の切り替え（本館・海の館・川と湖の館）が出て、断面図とフロアガイドが選んだ建物のものに替わる。2段目は、選んだ階の展示室を縮小版つきのカードで並べ、上にその建物の断面図へ戻るボタンと、その建物の階の切り替えを置く。準備中の枠は、縮小版の窓のない低いカードで名前を出す。展示室が増えても、1段目に並ぶのは1つの建物の階の数だけで、展示室名が帯の中で切れない。前回の展示室があれば、1段目の見出しの下に、そこへ直接戻るボタンを出す。
- 階の呼び名は、建物の中の画面（その建物の断面図や階の一覧）では「3階」、館全体から見る画面（図鑑の「見られる水槽」、展示室の見出し）では「海の館 3階」と建物を付ける（`getFloorPlaceLabel`）。
- 断面図の絵は横長の概念図として抽象度を高くし、特定の生き物・水槽の数や形や部屋の仕切りは描かず、階ごとの水の色と光だけで表す（展示の中身や展示室の数が変わっても絵と矛盾せず、描き直さずに済むように）。各階の範囲は `building.json` の `floors[].mapArea`（絵の画素）に書く。絵を差し替えたら測り直す。狭い画面では `map.focus` の範囲（建物と階名の札）だけを切り出して大きく見せる。断面図の帯とフロアガイドは、どちらかに触れると同じ階が光り、その階の配置を先読みする。
- 階の一覧の開いている展示室には、その展示室の画面の縮小版（`src/ui/HallPreview.tsx`）を映す。展示室の絵を水槽の並びのあたりで2:1に切り取り、各ガラスに今の水景の小さな画像（`thumb.webp`。館内図では `plate.webp` を読まない）を展示室の画面と同じ置き方（`framePlate`）で重ねるので、水景や展示室の絵を変えても縮小版を作り直す必要はない。魚はこの大きさでは見えないので描かない。準備中の枠は破線のカードで名前と「準備中」を出す。
- 展示室の絵は、展示館の内装で描き直す（暗めの展示室、解説パネル、階ごとに違う内装の色）。ガラスの位置も測り直す。
- 1つの展示室で同時に動かす水槽は6台までとする。それを超える場合は展示室を分ける（iPhone で全水槽を同時に描くため）。

#### まだ見ていない水槽と生き物の印（NEW。2026年10月11日に実装）

水槽が増えても、まだ見ていないものがどこにあるかを、館内図から水槽までたどれるようにする。

- **未読の定義**: 生き物は、その水槽の「既読の種の並び」にない種（水槽ごとに数え、同じ種が別の水槽にいても別）。水槽は、未読の種が1つでもある水槽（見たあとに種が足された水槽も含む）。展示室・階・建物は、下に未読の水槽が1つでもあるもの（準備中の枠は数えない）。
- **既読になるとき**: 水槽の画面に入った時点で、その水槽の今の種がすべて既読になる（`TankScreen` は水槽ごとに作り直すので、隣の水槽へ移ったときや `?tank=` で直接開いたときも同じ）。展示室の画面を見ただけでは消えない。入った時点で未読だった種の行には、水槽を出るまで印を残す。水槽から外れた種の既読は残す。
- **印を出す場所**: 館内図の1段目（建物の切り替え、断面図の階の帯、フロアガイドの階の行。階の行には未読の水槽の数）、2段目（階の切り替えの点、展示室のカードに未読の水槽の数）、展示室（水槽の枠の上と、下の目録）、水槽の設定パネルの生き物の行。図鑑には付けない。印は `src/ui/NewMark.tsx`（`.new-mark`）で、読み上げには「未読の水槽が5台」のような文を渡す。
- **データ**: 判定は `src/core/seen.ts`（純粋な関数と、薄い保存層）。既読は `localStorage` の `tropical-aquarium.seen.v1` に `{ 水槽id: 既読の種idの配列 }` で持ち、水槽の設定（`AQUARIUM_STATE_STORAGE_KEY`）とは分ける。React では `src/useSeenTanks.ts` が1か所で持ち、`App` から館内図・展示室・水槽の画面へ未読の一覧を渡す。水槽ごとの今の種の並びは `virtual:tank-species` を起動後に読む（読めるまで・読めないときは印なし）。
- **最初の状態**: 既読の保存がない・読めない・壊れているときは、`src/content/museum/seen-baseline.json`（閲覧の記録を取り始めた2026年10月10日の終わりに館にあった水槽と種。Git の履歴から書き出した）を既読として始める。このファイルは書き足さない（あとから足した水槽と種が未読になる）。水槽を見るまでは保存しない。
- 画面の確かめは `bun run verify:webview -- --halls=<展示室>` に入っている（印が館内図・階の一覧・展示室・設定パネルに出て、水槽に入ると消え、開き直しても消えたまま）。

### 2. 画面遷移をURLで持つ（実装済み）

館内図はクエリなし（本館の断面図）と `?building=<建物>`（ほかの建物の断面図）、階の一覧は `?floor=`、展示室は `?hall=`、水槽は `?tank=`（`?theme=` で水景を指定しても開ける）、図鑑は `?zukan` と `?zukan=<種>`。何も指定せずに開くと本館の館内図から始まる。階・展示室・水槽の id は館全体で重ならないので、`?floor=`・`?hall=`・`?tank=` に建物は書かない。History API で戻る・進むが効き、隣の水槽・隣の階・隣の建物への移動は履歴を増やさない。展示室の「館内図」ボタンと Esc は、その展示室の階の一覧へ戻り、階の一覧の Esc は、その階のある建物の断面図へ戻る。GitHub Pages で動くよう、パスではなくクエリで表す。

  ヒトデ・ウニ（2026年10月9日。アオヒトデ、サンフラワーシースター、ガンガゼ、キタムラサキウニ）は、動き（性質）が同じで、絵の視点が違うので描き方を2つに分けた。どちらも面を歩く仕組み（`src/core/surfaceMotion.ts`）でごくゆっくり這い（`speedBodyLengthsPerSec.cruise` が体の長さの0.4〜1%/秒）、`bottomRest` と `grazing` で長く止まる。前後がないので、描き方は向き（yaw）で絵を反転しない。`swim.radial` に体の中心（`x`・`y`）、動かさない体の半径（`radius`。ヒトデの盤、ウニの殻）、腕の先・棘の先までのふつうの距離（`reach`）を書く（半径と距離は画像の横幅に対する比率）。面の多くは奥へ向かって上がる線で、画面の上では坂に見えても実際は平らなことが多いので、面の傾きに合わせて体を回す割合（`BodyPlanRenderer.surfaceTilt`）を0.3にし、坂の面で体が立ち上がって見えないようにした。ヒトデ（`seaStar`）は dots の真上から見た画像（`sea-star-dorsal-natural-photo.v1`）を縦に0.5倍へ縮めて斜め上から見下ろした姿にする。描き方（`src/render/bodyPlans/seaStar.ts`）は、腕を盤の縁から先の4割までまっすぐ保ち、そこから先を一様な弧で反らせて先を持ち上げる（`swim.tailSweepRad` が反らせる角度）。這う間は進む側の腕ほど高く持ち上げ（進む向きは yaw から取るので、折り返すときは持ち上げる腕が手前を回って滑らかに移る）、ほかの腕の先は体の周りを巡る波（`swim.waveCount` 個、`swim.tailBeatHz` の拍）でゆっくり上下する。休む間は動きを小さくし、食べる間（forage）は腕の先を下ろして盤を少し盛り上げる。柔らかい腕は体の面の中でもしなる（`swim.verticalFlex`）。這う間は体の面の中で少しずつ回る（`MotionState.spin`。回る向きは数分ごとに入れ替わる）。位置は盤の中心から見下ろした姿の手前へ腕の長さの0.6倍ずらした固定の点（`BodyPlanRenderer.pivot`）で、手前の砂の面でも手前の腕がガラスの下端で切れにくい。叩いても反応しない（startle の `none`）。ウニ（`urchin`）は dots の斜め上から見た画像（`sea-urchin-oblique-natural-photo.v1`）を、接地点（`swim.footAnchor`。殻の下の縁）を中心に縦に0.85倍へ縮める。描き方（`src/render/bodyPlans/urchin.ts`）は、殻を動かさず、殻の縁より外の各頂点を殻の中心のまわりに小さく回して、棘を付け根から傾ける（先ほど大きく）。傾きは殻の周りを巡る2つの波の和で、`swim.tailSweepRad` が振れ角。這う間は下側の棘を歩みに合わせて動かす。叩くと（startle の `hunker`）立ち止まり、`alarmSec` の間は棘を2.2Hzで細かく震わせる。位置は接地点に固定する。

  巻貝・ウミウシ（2026年10月9日。カバクチカノコガイ、ゼブラ石巻貝、チャイニーズミステリースネール、オオタニシ、アオウミウシ）は、dots の斜め上から見た画像（`gastropod-oblique-natural-photo.v1`。頭が左）を使う。殻のある巻貝も殻のないウミウシも同じ視点なので、描き方は1つにし、殻の有無で分ける。`swim.shell` に殻を楕円の和で書き（`x`・`rx` は画像の横幅、`y`・`ry` は高さに対する比率。螺塔の高い殻は体層と螺塔に1つずつ）、殻のないウミウシは書かない。`swim.feelers` に頭の触角（`tentacle`）、ウミウシの背の触角（`rhinophore`）と鰓（`gill`）の付け根（`base`）・先（`tip`）・動かす範囲の半幅（`width`）を書く。`swim.footAnchor` は足の裏が面に着く点で、`realBodyLengthCm` は画像の横幅（触角を含む）、図鑑の `adultSizeCm` は殻長・殻高（ウミウシは体長）。動きは面を歩く仕組み（`src/core/surfaceMotion.ts`）をそのまま使い、体の長さの4〜7%/秒でごくゆっくり這い、`grazing`（面を削って食べる）と `bottomRest` で長く止まる。叩くと（startle の `hunker`）立ち止まり、性質 `hunker`（構えている秒数の幅と、構えを解いてから歩き出すまでの秒数。巻貝は6〜14秒と4秒。書かない体のつくりは3〜7秒と0.5秒）の間こもる。描き方（`src/render/bodyPlans/gastropod.ts`）は、殻（楕円の内側）を動かさず、殻の外の軟体（頭と足）を這う拍（`swim.tailBeatHz`）に合わせて伸び縮みさせる（頭と足の前が画像の横幅の2.5%ほど前へ伸び、足の後ろが遅れて縮み、殻は足の上でかすかに揺れる）。触角・鰓は付け根を軸に、先ほど大きく曲げて揺らし（`swim.tailSweepRad` が振れ角。這う間は大きく）、鰓はゆっくり膨らむ。足の下の縁（ウミウシは外套膜の縁）は、頭から尾へ送る波（`swim.waveCount` 個、振れ幅 `swim.verticalFlex`）で波打つ。ついばむ間（forage）は頭を面へ下げて歯舌で削る拍を付け、触角の先を下ろす。叩かれると、触角を付け根へ縮め、殻の外の軟体を殻の楕円の縁の少し内側へ集めて引っ込め、殻を足の裏の高さまで下ろす（切り抜きは使わず、メッシュを潰して隠す）。構えを解くと数秒かけて体を出し、触角は最後に伸びる。ウミウシは触角と鰓を縮め、体を短く丸める。位置は足の裏の固定の点（`BodyPlanRenderer.pivot`）で、面の傾きに合わせて体を回す割合（`surfaceTilt`）は0.6。向きを変えるときは、ほかの面を歩く生き物と同じく画像を反転する。メッシュの縦の分割は16で、殻の楕円の縁の近く（正規化した距離0.98〜1.1）は殻と軟体の動きが混ざるので、引っ込める間は殻の縁がわずかに潰れる。

  メンダコは腕の間の膜を広げて泳ぐので、`jelly` の体のつくりで、絵全体を傘（`bell: { top: 0, bottom: 1 }`）として拍動させる。`bottomRest` の習性を持つ漂う生き物は、生活層の下寄りにいるときにときどき底に降りて伏せ、休み終えるとまた漂い出す（`src/core/driftMotion.ts`）。

- **描き方（render）**: `src/render/bodyPlans/` に体のつくりごとのファイルを置き、メッシュの縦の分割数と毎フレームの変形を書く。`index.ts` の `BODY_PLAN_RENDERERS` に登録する。
- core の `BODY_PLANS` に足した体のつくりが描き方の表になければ型エラーになり、`bodyPlans.test.ts` でも検出する。

新しい体のつくりを足す手順:

1. 足す生き物の動きを公開資料で調べ、今の性質で表せるか確かめる。表せない動きは、性質を1つ足し、simulation などで性質を見て分岐する（体のつくりの名前で分岐しない）。
2. `BODY_PLANS` に性質を書く。
3. `src/render/bodyPlans/<id>.ts` に変形を書き、`BODY_PLAN_RENDERERS` に登録する。
4. `species.json` の `swim.bodyPlan` に指定し、テストと画面で確かめる。

保管庫にある視点で、まだ描き方のないもの: 二枚貝、イソギンチャク、ウミユリ、等脚類、水生昆虫、カブトエビ、ヒラメ・カレイ（有眼側）、渓流の平たい魚（背面）。ゆっくり這うもの、その場で揺れるものは、まとめて1つの体のつくりにできるかもしれない。

### 4. 水の種類をデータで決める

冷たい水、深海、洞窟、汽水、陸と水があるパルダリウムでは、水中フィルターの色、光の筋、コースティクス、浮遊物、水面の見え方が違う。これをコードの分岐ではなく、`scene.json` の `water` に持つ（水温帯、透明度、光の届き方、浮遊物の量、発光の有無など）。照明の選択肢も水の種類に合わせて変えられるようにする（深海では自然光を出さない、など）。

**水面の高さ（実装済み）**: 水面の上の空気まで見える水景は、`scene.json` の `waterLine` に水面の高さを持つ（背景画像に対する比率。`front` はガラス側、`back` は奥で水面が見える高さ。奥ほど上に見える）。シミュレーションは `src/core/waterColumn.ts` で奥行きごとの水面の高さを求め、次のように扱う。

- 泳ぐ層（`preferredZone`）の上下は、水槽全体ではなく水の部分に対する比率として当てる。初期配置も同じ比率で水の部分へ置く。
- 魚は水面より上へ泳ぎ出さない。空気呼吸（`airBreathing`）の行き先は水面、驚いて逃げる先も水の中。
- 巣穴など地形の目的地は水の外に置いてもよい（干潟の巣穴）。向かう間は水面で止めず、出たあとは止まらずに水へ戻る。
- 水面のすぐ下まで岩があるところでは岩を優先し、押し上げられた分だけ水面の余白に入ってよい。
- 水中の浮遊物は手前の水面より下にだけ漂わせる。

### 5. 図鑑のデータ

`species.json` の `catalog`（学名、原産地、性質、動き、生息環境）を土台に、`profile` を足す。

- 分類（目・科）、成体の大きさ、分布、生息環境の水温と水質
- `keeping`: 家庭で飼育される / 公共水族館で展示される / 展示例がほとんどない（深海など）
- 保全状況（IUCN レッドリストの区分。出典つき）
- 見どころ（この展示で観察できる行動。`ecology.habits` と対応させる）
- 出典は今の `ecology.sources` と共通にする

文章は公開資料に基づき、出典のない数値は書かない。

**画面（実装済み）**: `src/ui/Zukan.tsx`。全種の一覧（展示順・分類順・名前順、淡水・汽水・海水で絞り込み）、検索（名前、かな、学名、別名、目・科、原産地）、1種ずつの解説、見られる水槽（そこから水槽へ移る）。`?zukan` で一覧、`?zukan=<種>` で解説を、館内図の上に開く。図鑑の中で進んだ数を履歴に持ち、閉じるとその分だけ戻る。収集や達成の仕組みは付けない。

- 一覧は、ビルド時に species.json から作る全種の見出し（`virtual:species-index`。`vite/contentModules.ts` と `src/core/speciesIndexEntry.ts`）だけで描き、図鑑を開いたときに1つのチャンクとして読む（254種で約120KB、gzip 24KB。体の画像の URL の表 `virtual:fish-images` も一緒に読む）。見出しには、見られる水槽（`tankIds`）と展示順（`exhibitRank`）もビルド時に入れる。解説を開いたときに、その種のモジュール（`virtual:species/<id>`）を読む。
- 種数は、表示用の学名とは別の「種として数えるキー」（`speciesKey`）で数える。亜種は種にまとめ、未同定（sp.）・種群・流通名は数えない。

### 6. アセットの保管庫と制作キュー

数百種の画像を外部のエージェントに夜間などにまとめて作らせ、手元で確かめて取り込めるようにする。原画はリポジトリの外の保管庫（非公開リポジトリ `sakataka/aquarium-assets`）に置き、このリポジトリには配信用の `body.webp` と `plate.webp` だけを入れる。今の `side.png` は合計55MBあり、数百種では数百MBになるため。フォルダ構成、依頼の書式、状態の進め方、取り込みの手順は [アセットの保管庫](asset-vault.md) にまとめる。

### 7. 展示計画との突き合わせ（実装済み）

「図鑑に載る種は、館のどこかの水槽で必ず見られる」を守るには、種を受け入れる前に、その種の入る水槽が計画にあることが要る。展示計画（保管庫の `catalog/exhibit-plan.json`）は、館 → 建物（`buildings`）→ 階（`floors`。`buildingId` で建物を指す）→ 展示室 → 水槽の正本で、水槽ごとに、保管庫に画像のある種（`species`）、体のつくりを待つ種（`futureSpecies`）、これから dots に調べてもらう種の手がかり（`candidates`。和名・学名・役割）、何を見せる水槽か（`storyJa`）、水景の説明（`sceneEn`）を持つ。アプリは、そのうち開いた分（`room/*.json`・`tank.json` のあるもの）を持つ。

`bun run plan:check`（`scripts/check-exhibit-plan.ts`）が、計画とアプリを突き合わせる。保管庫はリポジトリの外にあるので、テストではなくスクリプトにしている。食い違いがあれば終了コード1で終わる。

- 館内図の建物・階・展示室の枠（`building.json`）が、計画と同じ並びであること。
- アプリの水槽が計画の同じ展示室にあり、アプリの水槽の種が、計画のその水槽の `species` に入っていること。
- 保管庫のカタログにある種が、どれも計画のどこかの水槽に置かれていること（置き場所のない種を作らない）。
- 器の数（建物ごとの展示室・水槽・種の、開いている数と計画の数）と、計画で水槽が決まっていて館にまだいない種（その水槽が開いていれば「取り込める」、まだなら「水槽を待つ」）を表示する。

館の中の検査（全種がどこかの水槽の既定の匹数に入っている）は、これまでどおり `content.test.ts` が確かめる。

### 数百種に耐えるための決まり（2026年10月5日に実装、10月7日に作り直し）

起動時に読むものを、館内図に要るものだけに絞る。展示室の中身は、その展示室に入るときに読む。内容ファイル（`src/content/`）はビルド時に `vite/contentModules.ts` が読み、zod で形と参照（水槽の水景と生き物、展示室の水槽、館の枠）を検証して、次のモジュールを作る。形の定義は `src/core/contentSchemas.ts`（生き物は `src/core/schema.ts`）にあり、ビルドとテストで使う。アプリは検証済みの内容を読むだけで、起動時に zod を読まない。

| モジュール | いつ読むか | 中身 |
|---|---|---|
| `virtual:museum`（`core/museum.ts`） | 起動時 | 館（`museum.json`）と建物・階・展示室の枠（`buildings/<id>/building.json`）、展示室の見出し（名前、階、水槽の並び、生き物の数）、階ごとの生き物の数、水槽の見出し（名前、展示室、選べる水景）、階と展示室を読む関数 |
| `virtual:floor/<id>`（`core/museum.ts` の `loadFloor`） | 館内図で階を開くとき（触れたときに先読み）と、その階の展示室に入るとき | その階の展示室の部屋の絵のガラスの位置と縮小版の画像、その階の水景の見出し（縮小版の画像、既定の照明、切り取り方） |
| `virtual:hall/<id>`（`core/catalog.ts` の `loadHall`） | 展示室に入るとき | 水槽の定義、水景（見出し、地形、`plate.webp` の URL）、生き物の定義、部屋の絵の URL。1つのチャンクにまとめ、入るときの読み込みを1回にする（階のモジュールと並べて読む）。読み終わるまでは「展示室を準備しています」を出す |

| `virtual:species-index` | 図鑑を開くとき | 全種の見出し（上の「図鑑のデータ」） |
| `virtual:species/<id>` | 図鑑で解説を開くとき | 生き物1種の定義 |
| `virtual:tank-species`（`core/seen.ts` の `loadTankSpecies`） | 起動のすぐあと（最初の描画のあと） | 水槽ごとの今の種の並びと、既読の最初の状態（`museum/seen-baseline.json`）。まだ見ていない水槽と生き物の印（NEW）に使う。生き物の数で増えるので、館の索引には入れない |

- 最初に読む JS は 285KB、gzip で89KB（2026年10月7日、18室・70水槽・78水景・254種）。react が約219KB、館の索引が約20KBで、残りがアプリの画面と保存。以前は 640KB（gzip 188KB）で種と水槽の数に比例して増え、10月7日の分割で 314KB（gzip 99KB）になり、同じ日にガラスの位置と水景の見出しを階のモジュールへ移して今の大きさになった。館の索引は展示室と水槽の数に比例し、生き物と水景の数では増えない。10月10日に建物の段と、新しい2つの建物の階・準備中の展示室の枠32室を足して 299KB（gzip 93KB）。館の索引は約27KB で、約250水槽・50室がすべて開いても 55KB 前後（gzip 15KB 前後）の見込み。それより大きくなったら、水槽の見出し（`?tank=` の解決に使う）を建物ごとのモジュールに分ける。10月11日に未読の印（NEW）を足して 304KB（gzip 93KB。増えたのは約2.5KB）。水槽ごとの種の並びは別のモジュール（`virtual:tank-species`。96水槽で約20KB、gzip 5KB）にあり、最初に読む JS には入らない。階のモジュールは1階分が 2.5〜10KB（gzip 1〜5KB）。
- `package.json` の `sideEffects`（CSS だけに副作用がある）で、`src/core/index.ts` から再輸出しているだけで館内図では使わないシミュレーションなどを、最初のチャンクから外している。CSS 以外で、読み込むだけで効くモジュールを作らない。
- 保存データの水槽ごとの設定は、その水槽のある展示室に入るときにそろえる（`normalizeHallCustomizations`）。起動時には、水景がその水槽で選べるか（選べなければ最初の水景にして照明を残す）と照明の形だけを確かめ、照明の壊れた水槽の設定は落とす（既定の照明は階のモジュールにあり、起動時には分からないため）。入ったことのない展示室の水槽の設定は持たない。館内図の縮小版は、設定がなければ水槽の最初の水景を映す。
- 前の展示室のテクスチャ（部屋の絵、水景、魚）は、展示室を移ったときに GPU から外す（`render/assets.ts` の `releaseTexturesExcept`）。館内図にいる間は、直前の展示室の分を残す。
- 館内図の縮小版は、部屋の絵の小さな版（`room/thumbs/`、幅960px）と水景の `thumb.webp` だけを読み、画面外のものは遅れて読む。
- 魚種・水槽・展示室の追加は、これまでどおりファイルを置くだけで済み、中央の一覧ファイルを編集しない。開発サーバーでは、内容ファイルを足す・変える・消すとモジュールを作り直して読み直す。参照切れや形の誤りは、ビルドと開発サーバーがファイル名つきで止める。
- テストは `src/core/testSetup.ts` で全展示室と全生き物を先に読んでから検査する（`getLoadedTanks`）。
- 内容のモジュールは、自分が使う内容ファイルだけを監視に登録する（`vite/contentModules.ts` の `sourceFiles`）。全モジュールに全ファイルを登録すると、種の数×ファイルの数に比例して遅くなる（373種のときに、全種を読むテストの準備が毎回11秒かかっていた）。
- 1フレームの重さは `bun run measure:perf` で測り、基準値と比べる（[性能の計測と基準値](performance.md)）。計算の量は生き物の数に比例するので、展示室1室の既定の匹数を180匹までにしている限り、種が増えても1フレームは重くならない。
