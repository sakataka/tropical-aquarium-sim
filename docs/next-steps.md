## 方針

- **約1,300〜1,500種を前提に設計する。** 当面の目標は第1弾の約250〜300種を完成させることだが、作り方は1,300〜1,500種で破綻しない形を選ぶ。種数そのものにはこだわらず、「ふつうに見聞きする水の生き物はひととおりそろった」と感じられる館を目指す。
- **図鑑に載る種は、どれも館のどこかで必ず見られるようにする**（2026年10月8日、ユーザーより）。少なくとも1つの水槽に、最低1匹でよいので展示する。図鑑からのリンクで飛べる必要はない。そのための水槽・展示室・建物の数、拡張性、性能、アーキテクチャを考える（[ロードマップ](roadmap.md#どの種も館のどこかで必ず見られる2026年10月8日ユーザーより)）。
- **互換性は気にしない。** 保存データ、水槽ID、展示室ID、ファイルの形は、よりよい設計のためなら変えてよい（利用者は開発者本人だけ）。古い保存データの移行処理も消してよい。
- **データで決める。** 展示室・水槽・水景・生き物は `src/content/` のファイルを置けば読み込まれる形を保つ。中央の一覧ファイルを手で編集する形にしない。取り込みはスクリプトで行う（[アセットの保管庫](asset-vault.md#展示室を開ける流れ)）。
- **画像は数で作り手を選ぶ。** まとまった数の画像（生き物、水景、展示室の絵）は dots が作る。足りない画像や直してほしい点は、保管庫で dots に伝える（下記）。1〜2枚程度の少ない画像（館内図の断面図の描き直し、単発の差し替えなど）は、Codex の画像生成で作ってもよい（Claude Code からは `codex exec`。2026年10月7日、ユーザーより）。アプリのコードで絵を描いて代用しない（[AGENTS.md](../AGENTS.md)）。
- 起動時に読むものを増やさない。展示室の中身は、その展示室に入るときに読む。

## 作業の始めに

1. このリポジトリで `git pull` する（別のエージェントが直したコミットが入っていることがある）。
2. `cd ~/Documents/aquarium-assets && git pull` のあと、`notes/to-claude-code/` を見る。`consumer/replies/` に同じ名前の返事がないものが未対応。ユーザーが「どっち」と言うときは、音声入力で dots のこと。
3. 判断を返す。返事は `consumer/replies/<同じファイル名>` に置く。不足や不備は、返事か、`revisionTarget` 付きの修正依頼（`queue/requests/app-review-NNN.b1.json`、`queue/schemas/request.schema.json` で検証する）で伝える。
4. 採否は `adoptions/` に記録する。保管庫の変更も commit・push する。

## 届いた生き物を取り込む手順

1. **確かめる**: 未採否の種の最新草案（`species/<id>/meta.json` の `variants`）を、灰色の背景に重ねたコンタクトシートで目視する。外接矩形と余白（alpha 16 を超える画素、四辺48px）も数値で見る。依頼文（`catalog/*.json` の `subjectEn`）と模様・ひれの数が合っているかを見る。
2. **採用を記録し、取り込む**: `adoptions/<id>.json` を書き、`AQUARIUM_ASSET_VAULT=~/Documents/aquarium-assets uv run scripts/install-vault-species.py <id>...` で `content-drafts/fish/` に入れる。
3. **下書きを書く**: `species.json`（`profile` を含む）を調査（research.json）から書く。5種ずつサブエージェントに分けると速い。事実は調査に出典のあることだけを使い、動きの値は近い既存種に合わせる。分類の和名は既存の種にそろえる。`src/core/drafts.test.ts` が形を検証する。
4. **水槽に入れる**: 展示計画（`catalog/exhibit-plan.json`）の水槽の `species` に足し、`content-drafts/fish/<id>/` を `src/content/fish/` へ移し、`tank.json` の `species`・`defaultStock` に足す。図鑑の一覧には自動で載る。

## 展示室や水槽を足すとき（地形づくりの注意）

手順は [アセットの保管庫](asset-vault.md#展示室を開ける流れ)。地形（`terrain.json`）は1水槽ずつ絵を見て作る。展示室ごとにサブエージェントに分けて並行して作り、次を守らせる。

- 見える範囲（ガラスの縦横比で cover し、`framing.plateBottom` を下端に合わせた範囲）を切り出した絵で座標を決め、地形を重ねた確認画像で合わせる。
- 回避領域（obstacles）は魚の体長×0.2 だけ広げて判定される。楕円どうしの重なりのくぼみや、楕円とガラス・底の細いすき間に魚が挟まると、押し出されて位置が飛ぶ（耐久テストで落ちる）。大型魚の水槽ほど、大きな楕円を少数置き、壁や底まで覆う。
- 隠れ場所は、どの魚の体長で判定しても回避領域の内側に入らない奥行きに置く。`homeShelter` の魚がいる水槽には、その種類の隠れ場所が要る。
- エビなど面を歩く生き物は、端点でつながった面しか移れない。
- 水面の上の空気まで見える絵なら、`scene.json` に `waterLine`（手前と奥の水面の高さ）を書く。泳ぐ層は水の部分に対する比率になるので、空気の分を避けて層を下げない。回避領域の上端が水面のすぐ下まで来ると、魚が水面との間に挟まりやすい。
- テストは最初の失敗で止まるので、担当の水槽だけに絞った一時テストを作って流し、終わったら消す。
- 名前は「〜水槽」、`category` は生息地の名前、照明は夜行性の多い水槽なら `evening` も検討する。
- 展示室1室の既定の匹数は合計180匹までを目安にする（iPhone で全水槽を同時に描くため）。

## 次にやること（優先順）

新しいスレッドには、番号を指定して頼む。

1. **魚以外の体のつくり（続き）**: 準備中の4水槽を開けるため、クリオネ（clione-30。保管庫にハダカカメガイの画像と調査がある。翼足で羽ばたく。クラゲの漂い方に羽ばたきの描き方を足せば近い）、両生類（giant-salamander-240）、カブトガニ（horseshoe-crab-180）、エイ、チンアナゴ（砂から出入り）と順に足す。reef-invertebrates-90 はフリソデエビ（エビの描き方で描ける）とカニで開けられるか検討する。手順は [設計の「体のつくり」](museum-architecture.md#3-体のつくり実装済み)。保管庫に画像と調査がある種から採用する。保管庫に画像があり、まだ置いていないカニは5種: キンチャクガニ・イソギンチャクカニダマシ・ソメンヤドカリ（サンゴ礁。共生の展示室か reef-invertebrates-90）、タカアシガニとキワ・ヒルスタ（深海。タカアシガニは脚を広げると3mを超えるので、置くなら大水槽）。タコ・イカで足りないもの: 擬態の色変わり、腕で獲物を探る動き、巣穴への出入り、イカの群れの間合い（120cm水槽の36cmのアオリイカは重なって見えやすい）。カニの描き方で足りないもの: 干潟の岸と水中のどちらの面を歩くかを種で選べない（ハクセンシオマネキが水中も歩く）、シオマネキの雄のウェービング、巣穴への出入り。クラゲで足りないもの: クシクラゲの櫛板の虹色のきらめき（今は体が揺れるだけ）、アトラクラゲなどの発光。深海のクラゲ水槽はアトラクラゲだけなので、深海のクラゲ（保管庫に届いたら）を足す。
2. **シミュレーションの不具合と不足**: 休んでいる魚が少しずつ岩の内側へ入り、外へ押し出されて位置が飛ぶ（今は地形の調整でテストを通している）。岩に吸着して休む習性がない（ダンゴウオが砂の上で休む）。大型魚が水槽に対して大きすぎて縁で切れる（深海の大型種）。`terrainMotion.test.ts` の「every water scene has usable terrain…」がときどき落ちていたのは、時間切れだった（全水槽を回すので、70水槽で単独27秒、上限30秒。2026年10月8日に上限を90秒にした）。
3. **1,300種に合わせた館の拡張計画**: 展示計画（保管庫の `catalog/exhibit-plan.json`）を約200水槽・35室前後に広げる（別館や東西の翼）。「図鑑の全種がどこかで見られる」原則（上の方針）を守れる器の数を、種の受け入れより先に用意する計画にする。建物の段（別館・翼）を足しても館内図・URL・データの形を作り直さずに済む設計もここで決める。今は `content.test.ts` が「全種がどこかの水槽の既定の匹数に入っている」ことを確かめている。上の「dots と約束したまま残っていること」の水槽と、採用候補の種の置き場所もここで決める。展示室と水槽の絵は dots に頼む。
4. **地形づくりの省力化**: 1水景ずつ手で輪郭を取るのが律速。dots に水景と一緒に前景のマスク（手前の岩・流木の領域）や底の線を出してもらい、遮蔽と面を自動で作る仕組みを検討する（今ある水景の絵から推定できるかも試せる）。
5. **後始末**: 古い35種の `catalog.aliases` に入っている ID と学名そのもの（図鑑では表示時に除いている）を消す。
6. **規模への備え**: 数百種を超えたら、配信用画像の置き場所（Git の履歴の重さ）とテスト時間（今は `bun run test` で約110秒。全水槽を回す耐久テストは単独で約30秒）を見直す。館の索引は約20KB（254種・70水槽）で、展示室と水槽の数だけで増える。水槽画面と設定パネル（約12KB）も、展示室に入るときに読む形にできる。

## 検証

- 変更ごとに `bun run test`、`bun run build`（型検査を含む）を通す。魚を生む `createFishFromStock` は、渡さなければ `Math.random` で個体差を決めるので、多くのテストは実行ごとに少しずつ違う魚で走る。たまにだけ落ちるテストは、乱数を渡して（`simulation.test.ts` の `seededRandom`）再現し、何回中何回落ちるかを測ってから直す。画面の検証は影響範囲に合わせて選ぶ（2026年10月8日、ユーザーより）。
  - 水槽・展示室・生き物を足すなど、影響が特定の展示室に収まる変更は、`bun run verify:webview -- --halls=<展示室id>,...`（その展示室を 1440×960 と 420×912 で開き、広い画面では全水槽に出入りする。1室で約1分）。狭い画面で開くのは展示室の最初の水槽だけなので、ほかの水槽の狭い画面はブラウザで見る。
  - 描画の共通部分、画面の配置、画面遷移・URL、読み込みの仕組み、館内図・図鑑など、設計が大きく変わる変更は、`bun run verify:webview`（全展示室・全水槽・図鑑・履歴。20分ほどかかる）。
- 画面検証の実行中は、開発サーバーの再読み込みで結果が崩れるので、ソースを編集しない（文書の編集はよい）。
- ブラウザで見るときは localStorage を消してから見る（古い既定の匹数が残るため）。アプリ内のブラウザの枠が隠れていると描画が止まり、水槽が「10秒たっても準備が終わりません」になる。不具合ではないので、水槽の画面は枠を見える状態にするか、画面検証で確かめる。
- 変更は検証のあと commit・push する。保管庫の変更も同様。
