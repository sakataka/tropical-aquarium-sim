## 方針

- **約1,300種を前提に設計する。** 当面の目標は第1弾の約250〜300種を完成させることだが、作り方は1,300種で破綻しない形を選ぶ。
- **互換性は気にしない。** 保存データ、水槽ID、展示室ID、ファイルの形は、よりよい設計のためなら変えてよい（利用者は開発者本人だけ）。古い保存データの移行処理も消してよい。
- **データで決める。** 展示室・水槽・水景・生き物は `src/content/` のファイルを置けば読み込まれる形を保つ。中央の一覧ファイルを手で編集する形にしない。取り込みはスクリプトで行う（[アセットの保管庫](asset-vault.md#展示室を開ける流れ)）。
- **画像は dots が作る。** アプリ側で画像を生成しない。足りない画像や直してほしい点は、保管庫で dots に伝える（下記）。
- 起動時に読むものを増やさない。展示室の中身は、その展示室に入るときに読む。

## 作業の始めに

1. このリポジトリで `git pull` する（別のエージェントが直したコミットが入っていることがある）。
2. `cd ~/Documents/aquarium-assets && git pull` のあと、`notes/to-claude-code/` を見る。`consumer/replies/` に同じ名前の返事がないものが未対応。ユーザーが「どっち」と言うときは、音声入力で dots のこと。
3. 判断を返す。返事は `consumer/replies/<同じファイル名>` に置く。不足や不備は、返事か、`revisionTarget` 付きの修正依頼（`queue/requests/app-review-NNN.b1.json`、`queue/schemas/request.schema.json` で検証する）で伝える。
4. 採否は `adoptions/` に記録する。保管庫の変更も commit・push する。

## 届いた生き物を取り込む手順

1. **確かめる**: 未採否の種の最新草案（`species/<id>/meta.json` の `variants`）を、灰色の背景に重ねたコンタクトシートで目視する。外接矩形と余白（alpha 16 を超える画素、四辺48px）も数値で見る。依頼文（`catalog/*.json` の `subjectEn`）と模様・ひれの数が合っているかを見る。
2. **採用を記録し、取り込む**: `adoptions/<id>.json` を書き、`AQUARIUM_ASSET_VAULT=~/Documents/aquarium-assets uv run scripts/install-vault-species.py <id>...` で `content-drafts/fish/` に入れる。
3. **下書きを書く**: `species.json`（`profile` を含む）を調査（research.json）から書く。5種ずつサブエージェントに分けると速い。事実は調査に出典のあることだけを使い、動きの値は近い既存種に合わせる。分類の和名は既存の種にそろえる。`src/core/drafts.test.ts` が形を検証する。
4. **水槽に入れる**: 展示計画（`catalog/exhibit-plan.json`）の水槽の `species` に足し、`content-drafts/fish/<id>/` を `src/content/fish/` へ移し、`tank.json` の `species`・`defaultStock` に足す。図鑑の一覧には自動で載る。

## 展示室や水槽を足すとき（地形づくりの注意）

手順は [アセットの保管庫](asset-vault.md#展示室を開ける流れ)。地形（`terrain.json`）は1水槽ずつ絵を見て作る。展示室ごとにサブエージェントに分けて並行して作り、次を守らせる。

- 見える範囲（ガラスの縦横比で cover し、`framing.plateBottom` を下端に合わせた範囲）を切り出した絵で座標を決め、地形を重ねた確認画像で合わせる。
- 回避領域（obstacles）は魚の体長×0.2 だけ広げて判定される。楕円どうしの重なりのくぼみや、楕円とガラス・底の細いすき間に魚が挟まると、押し出されて位置が飛ぶ（耐久テストで落ちる）。大型魚の水槽ほど、大きな楕円を少数置き、壁や底まで覆う。
- 隠れ場所は、どの魚の体長で判定しても回避領域の内側に入らない奥行きに置く。`homeShelter` の魚がいる水槽には、その種類の隠れ場所が要る。
- エビなど面を歩く生き物は、端点でつながった面しか移れない。
- 水面の上の空気まで見える絵なら、`scene.json` に `waterLine`（手前と奥の水面の高さ）を書く。泳ぐ層は水の部分に対する比率になるので、空気の分を避けて層を下げない。回避領域の上端が水面のすぐ下まで来ると、魚が水面との間に挟まりやすい。
- テストは最初の失敗で止まるので、担当の水槽だけに絞った一時テストを作って流し、終わったら消す。
- 名前は「〜水槽」、`category` は生息地の名前、照明は夜行性の多い水槽なら `evening` も検討する。
- 展示室1室の既定の匹数は合計180匹までを目安にする（iPhone で全水槽を同時に描くため）。

## 次にやること（優先順）

新しいスレッドには、番号を指定して頼む。

1. **起動時に読むJSを減らす**: 最初に読むJSが、426KB（35種）→ 640KB（254種、gzip 188KB）と種と水槽の数に比例して増えた。全水槽の `tank.json`、魚種ごとの画像URLと読み込み関数の表（`src/render/assetUrls.ts`、`src/core/catalog.ts`）が起動時に入っている。館内図に要る軽い索引（展示室・水槽の名前と数）だけを起動時に読み、水槽の定義と魚種の表は展示室ごとのチャンクに分ける。図鑑は全種の見出しを `virtual:species-index`（ビルド時生成、`vite.config.ts`）から読むが、一覧の画像URL（`getFishImageUrl`）と「見られる水槽」（`aquariumTanks`）は起動時の表に頼っている。分けるときは、画像URLと水槽の対応も図鑑の見出しの側へ移す。
2. **魚以外の体のつくり**: 準備中の14水槽を開けるため、カニ（エビの歩行を流用）から始め、クラゲ、タコ・イカ、タツノオトシゴ、エイ、両生類、チンアナゴ（砂から出入り）と順に足す。手順は [設計の「体のつくり」](museum-architecture.md#3-体のつくり実装済み)。保管庫に画像と調査がある種から採用する。カニの視点（真横か斜め上か）を決めて dots に参照を出す（ヤマトオサガニの甲の形の判断を、そのときまで保留している）。
3. **1,300種に合わせた館の拡張**: 1水槽5〜8種・1室6水槽までなら、約200水槽・35室前後になる。展示計画を広げる（別館や東西の翼）。館内図は、全体の断面図から階を選び、階の中の展示室を一覧する2段の形にする（今もスマホ幅では、4室並ぶ階の展示室名が途中で切れる）。展示室・水槽の追加は dots に絵を頼む。上の「dots と約束したまま残っていること」の水槽と、採用候補の種の置き場所もここで決める。
4. **地形づくりの省力化**: 1水景ずつ手で輪郭を取るのが律速。dots に水景と一緒に前景のマスク（手前の岩・流木の領域）や底の線を出してもらい、遮蔽と面を自動で作る仕組みを検討する。
5. **シミュレーションの不具合と不足**: 休んでいる魚が少しずつ岩の内側へ入り、外へ押し出されて位置が飛ぶ（今は地形の調整でテストを通している）。岩に吸着して休む習性がない（ダンゴウオが砂の上で休む）。大型魚が水槽に対して大きすぎて縁で切れる（深海の大型種）。
6. **後始末**: 古い保存データの移行処理（v4 からの移行、7水槽時代の構成の入れ替え）とそのテストを消す。`scripts/verify-webview.ts` の古い移行の検証も外す。古い35種の `catalog.aliases` に入っている ID と学名そのもの（図鑑では表示時に除いている）も消す。
7. **規模への備え**: 数百種を超えたら、配信用画像の置き場所（Git の履歴の重さ）とテスト時間を見直す。

## 検証

- 変更ごとに `bun run test`、`bun run build`（型検査を含む）を通す。画面に関わる変更は `bun run verify:webview`（WebKit。全展示室を 1440×960 と 420×912 で開き、全水槽と図鑑に出入りする。20分ほどかかる）。
- 画面検証の実行中は、開発サーバーの再読み込みで結果が崩れるので、ソースを編集しない（文書の編集はよい）。
- ブラウザで見るときは localStorage を消してから見る（古い既定の匹数が残るため）。アプリ内のブラウザの枠が隠れていると描画が止まり、水槽が「10秒たっても準備が終わりません」になる。不具合ではないので、水槽の画面は枠を見える状態にするか、画面検証で確かめる。
- 変更は検証のあと commit・push する。保管庫の変更も同様。
