## 方針

- **約1,300〜1,500種を前提に設計する。** 当面の目標は第1弾の約250〜300種を完成させることだが、作り方は1,300〜1,500種で破綻しない形を選ぶ。種数そのものにはこだわらず、「ふつうに見聞きする水の生き物はひととおりそろった」と感じられる館を目指す。
- **図鑑に載る種は、どれも館のどこかで必ず見られるようにする**（2026年10月8日、ユーザーより）。少なくとも1つの水槽に、最低1匹でよいので展示する。図鑑からのリンクで飛べる必要はない。そのための水槽・展示室・建物の数、拡張性、性能、アーキテクチャを考える（[ロードマップ](roadmap.md#どの種も館のどこかで必ず見られる2026年10月8日ユーザーより)）。
- **水槽の組み合わせは、説明できるストーリーがあればよい**（2026年10月9日、ユーザーより）。1つの地域にそろえるのが基本だが、「北半球の冷たい川のヤツメウナギを見比べる」「大陸ごとのハイギョを比べる」のように、水槽の名前と説明文で何を見せたいか分かる並べ方なら、地域をまたいでよい。水族館として見る人が違和感を持たないことを基準にする。種が増えると1地域にそろえきれない種も出るので、置き場所に迷ったら、ストーリーで説明できる既存の水槽を先に探す。
- **大きさなどの値は、調査の根拠を優先する**（2026年10月9日、ユーザーより）。水族館の紹介文などの出典の弱い値と食い違うときは、調査の値を使い、sizeNote に両方を書く。
- **水族館にいそうな生き物は載せる**（2026年10月10日、ユーザーより）。爬虫類・哺乳類・鳥（ウミガメ、ペンギン、アザラシ、イルカ、ワニ、カワウソなど）も載せる前提にする。明らかに水族館にいないもの（クジラ、カバ、水鳥など）は載せない。哺乳類などは動きを作るのが難しいので、体のつくりができるまでは展示計画の候補（`needs` つき）のまま置く。
- **改良品種は同じ種として数える**（2026年10月10日、ユーザーより）。金魚・メダカ・錦鯉などは、姿の違いとして複数置いてよいが、種の数は増やさない（展示計画の候補では `varietyOf`、アプリでは同じ `speciesKey`）。
- **外来種は「外来種の水辺」だけに置く**（2026年10月10日、ユーザーより）。オオクチバスやブルーギルを原産地の水槽に重ねて置かない。原産地の水槽で存在感の大きい種が出てきたら、そのときに考える。
- **見えない生き物だけの水槽は開けない。見えない生き物は、ほかの種が見える水槽でも置かずに保留にする**（2026年10月10日・11日、ユーザーより）。水槽に対して小さすぎたり、底の色に溶け込んだりして、画面でほとんど見つけられない生き物しかいない水槽は、準備中のままにする（一度開けたものは準備中に戻す）。完成までは時間がかかるので、少しずつ進めばよい。思いどおりに見せられない生き物は、その生き物に合う小さな水槽を展示計画に足すなど、拡張計画の中で置き方を考える。数字の決まりは作っていない（体長が水槽の幅の2〜3%でも、色のある群れで泳ぐテトラは見える。小さく、底にいて、底と同じ色の生き物が見えない）。水槽を開ける前に、画面検証の画像で生き物が見つけられるかを見る。
- **水槽の匹数は、実際の水族館と同じように見栄えとリアリティで決める**（2026年10月10日、ユーザーより）。極端に多い匹数は不自然なので、少なめでよい（テナガエビの川水槽の上限5匹のような数で構わない）。種を足して違和感が出る（詰まる、重なる、見えない）なら、無理に同じ水槽へ入れず、新しい水槽を展示計画に足す。
- **互換性は気にしない。** 保存データ、水槽ID、展示室ID、ファイルの形は、よりよい設計のためなら変えてよい（利用者は開発者本人だけ）。古い保存データの移行処理も消してよい。
- **器が先。** 種を受け入れる前に、その種の入る水槽が展示計画にあるようにする。置き場所のない種は `bun run plan:check` が食い違いとして出す。展示室や水槽を計画から変えるときは、先に展示計画を直す。
- **データで決める。** 展示室・水槽・水景・生き物・建物は `src/content/` のファイルを置けば読み込まれる形を保つ。中央の一覧ファイルを手で編集する形にしない。取り込みはスクリプトで行う（[アセットの保管庫](asset-vault.md#展示室を開ける流れ)）。
- **画像は数で作り手を選ぶ。** まとまった数の画像（生き物、水景、展示室の絵）は dots が作る。足りない画像や直してほしい点は、保管庫で dots に伝える（下記）。1〜2枚程度の少ない画像（館内図の断面図の描き直し、単発の差し替えなど）は、Codex の画像生成で作ってもよい（Claude Code からは `codex exec`。2026年10月7日、ユーザーより）。dots が止まっている間は、水景・展示室の絵など大きな画像なら数十枚まで Codex で作ってよい（2026年10月9日、ユーザーより）。既存の水景を参考画像として渡し、色味・光・描き込み密度をそろえる。生き物の画像を何百枚も作るのは、トークンの負担が大きいので Codex ではやらない（dots を待つ）。dots が戻ったら、元の分担に戻すかユーザーに確かめる。アプリのコードで絵を描いて代用しない（[AGENTS.md](../AGENTS.md)）。
- 起動時に読むものを増やさない。展示室の中身は、その展示室に入るときに読む。

## 届いた生き物を取り込む手順

1. **確かめる**: 未採否の種の最新草案（`species/<id>/meta.json` の `variants`）を、灰色の背景に重ねたコンタクトシートで目視する。外接矩形と余白（alpha 16 を超える画素、四辺48px）も数値で見る。依頼文（`catalog/*.json` の `subjectEn`）と模様・ひれの数が合っているかを見る。
2. **採用を記録し、取り込む**: `adoptions/<id>.json` を書き、`AQUARIUM_ASSET_VAULT=~/Documents/aquarium-assets uv run scripts/install-vault-species.py <id>...` で `content-drafts/fish/` に入れる。
3. **下書きを書く**: `species.json`（`profile` を含む）を調査（research.json）から書く。5種ずつサブエージェントに分けると速い。事実は調査に出典のあることだけを使い、動きの値は近い既存種に合わせる。分類の和名は既存の種にそろえる。`src/core/drafts.test.ts` が形を検証する。
4. **水槽に入れる**: 展示計画（`catalog/exhibit-plan.json`）の水槽の `species` に足し（計画中の水槽の `candidates` にあった種なら、そこから外す）、`content-drafts/fish/<id>/` を `src/content/fish/` へ移し、`tank.json` の `species`・`defaultStock` に足す。図鑑の一覧には自動で載る。`bun run plan:check` で食い違いがないことを見る。

## 展示室や水槽を足すとき（地形づくりの注意）

手順は [アセットの保管庫](asset-vault.md#展示室を開ける流れ)。地形（`terrain.json`）は1水槽ずつ作る。まず `uv run scripts/draft-terrain.py <水景id>` で下書きと確認画像を出し（[地形の下書きを絵から作る](terrain-drafting.md)）、絵を見て手直しする。展示室ごとにサブエージェントに分けて並行して作り、次を守らせる。

- 見える範囲（ガラスの縦横比で cover し、`framing.plateBottom` を下端に合わせた範囲）を切り出した絵で座標を決め、地形を重ねた確認画像で合わせる。
- 回避領域（obstacles）は魚の体長×0.2 だけ広げて判定される。楕円どうしの重なりのくぼみや、楕円とガラス・底の細いすき間に魚が挟まると、止まったり位置が飛んだりする（耐久テストで落ちる）。大型魚の水槽ほど、大きな楕円を少数置き、壁や底まで覆う。2026年10月9日に岩の判定の食い違いを直したので、この注意は緩められるかもしれない（まだ確かめていない）。
- 隠れ場所は、どの魚の体長で判定しても回避領域の内側に入らない奥行きに置く。`homeShelter` の魚がいる水槽には、その種類の隠れ場所が要る。
- エビなど面を歩く生き物は、端点でつながった面しか移れない。
- 水面の上の空気まで見える絵なら、`scene.json` に `waterLine`（手前と奥の水面の高さ）を書く。泳ぐ層は水の部分に対する比率になるので、空気の分を避けて層を下げない。回避領域の上端が水面のすぐ下まで来ると、魚が水面との間に挟まりやすい。
- 担当の水槽だけを確かめるには `bun run test:tanks -- -t <水槽id>`（上限匹数での昼夜20分を2通りの乱数で、既定の匹数での3分を1回。水槽1つで数秒）。水槽ごとのテストなので、ほかの水槽が落ちていても止まらない。
- 名前は「〜水槽」、`category` は生息地の名前、照明は夜行性の多い水槽なら `evening` も検討する。
- 展示室1室の既定の匹数は合計180匹までを目安にする（iPhone で全水槽を同時に描くため）。

5. **魚の泳ぎ方を型に分ける**（2026年10月8日、ユーザーとの話から）: 魚の描き方（`src/render/bodyPlans/fish.ts`）は1種類だけで、体の後ろ半分に波を送って尾を振る変形を、種ごとの数値（`tailBeatHz`・`bodyWaveStart`・`waveCount`・`tailSweepRad`・`verticalFlex`）で調整しているだけ。動き方（`gait`）も4つで、146種が `burstCoast`。後から足した体のつくりのように動きを調べて部位を動かす形にすると、ベラ・スズメダイの胸びれで漕ぐ泳ぎ、フグ・ハコフグの体を曲げずにひれで進む泳ぎ（タツノオトシゴの `swim.fins` が使える）、モンガラカワハギの背びれ・尻びれの波打ち、ウナギ・ウツボの体全体のくねり、ハゼの底で跳ねる進み方などを描き分けられる。泳ぎ方の型を体のつくり（または魚の下位の型）として足し、種に当てはめる。魚の種数が多いので、型ごとに当てはまる種を一覧にしてから進める。型を当てはめない種の絵が変わっていないことは、`bun run compare:render` で確かめられる。

8. **後始末**: 古い35種の `catalog.aliases` に入っている ID と学名そのもの（図鑑では表示時に除いている）を消す。
9. **性能の残り（急がない）**: [性能の計測と基準値](performance.md#まだやっていない効きそうなこと) に、効きそうな順に書いた。(a) iPhone の実機では測らない（2026年10月10日、ユーザーより）。当面は機能の追加を優先し、iPhone で重さが気になったときに調べて直す。(b) 狭い画面の展示室は、部屋の絵の全体（5.9 百万画素）を描いていて、見えているのはその4分の1。見えている範囲だけを描けば GPU の負荷が大きく減るが、iPhone の慣性スクロールで絵が遅れるおそれがあるので、実機で重いと分かってから。(c) 画像の量: `body.webp` は1種約 70KB、水景は1枚約 0.4MB で、今は合わせて 72MB、1,500種・254水槽で約 220MB の見込み。(d) 種や水槽をまとめて足したら `bun run measure:perf` を流し、計算の量が基準値から大きく増えていないか見る（増えたら原因を調べ、納得できる増え方なら `--update-baseline`）。
10. **生き物の情報を新しくする仕組み**（館がひととおりそろってから。2026年10月9日、ユーザーより）: 学名の変更、大きさ、分布、保全状況などの新しい知見を、図鑑と水族館の展示に反映できるようにする。事実は保管庫の調査（research.json、出典つき）にあり、図鑑の `profile` はそこから書いているので、調査の日付と出典の版を記録し、定期的に調べ直して前回との差分を一覧にし、確認したものだけ反映する形が考えられる。学名が変わったときのために別名（`catalog.aliases`）の仕組みはすでにある。
11. **水族館の情報モデル（中長期の検討。2026年10月10日、ユーザーより）**: 建築の BIM（Building Information Modeling）のように、水槽・水景・生き物・素材を「制約つきのモデル」として持ち、設計を制約の上で進められるようにする案。建築は条件が複合的で AI に任せにくいと言われてきたが、BIM で素材や制約をモデルにすると、その上の設計は AI の得意な仕事になる。同じことを水族館でやると、汎用性・応用性・リアリティが上がる見込みがある。今あるもの: 種のデータ（大きさ、水の種類、昼夜の活動、群れ、習性、住みか）、出典つきの調査（research.json。水温・水質・食性・混泳の注意が入っている種もある）、展示計画（水槽の大きさ・何を見せるか・候補）、地形（面・遮蔽・隠れ場所）、`plan:check`（計画とアプリの食い違いだけを見る）。足りないもの: (a) 生き物の側の条件を機械で読める形にすること（水温・塩分・水質の幅、必要な底質と隠れ場所、体長に対して必要な水槽の大きさと泳ぐ空間、食性と「食べる・食べられる」の関係、縄張りと同種の数、面を歩く生き物が詰まらない匹数）。いまは説明文と sizeNote に文章で書いている。(b) 水槽の側の条件（水温・塩分・流れ・底質・隠れ場所の種類と数・歩ける面の広さ）。(c) 2つを突き合わせる検査（「この水槽にこの種を何匹」の可否と理由を出す。実際の飼育で勧められない組み合わせは、説明文の断り書きを求める）。(d) その検査を使って、候補の種から水槽の組み合わせ・匹数・必要な水景の要素を提案させる流れ。まず検討すること: モデルの項目を research.json のどの欄から機械的に埋められるか（`evidenceStatus` が unverified・unknown の欄は条件にしない）、既存の約400種でどれだけ埋まるか、今回のテナガエビの水槽（8匹から立ち往生する。耐久テストでは見つからない）や「見えない生き物だけの水槽は開けない」（体長と水槽の幅、底と体の色）のような、いま人が画面で見て決めている判断のうち、どれを検査にできるか。館がひととおりそろう前でも、項目の設計だけ先に決めておくと、dots の調査の欄をそれに合わせられる。

## 検証

- 作業中は `bun run test:fast`（約6秒）と、関係する水槽の `bun run test:tanks -- -t <水槽id>`。commit の前に `bun run test`（全部。約30秒）と `bun run build`（型検査を含む）を通す。テストの間の `Math.random` は決まった乱数列なので、同じテストは毎回同じ魚で走る。乱数を揺さぶって探すときは `bun run test:fuzz`（使った値を表示する。落ちたら `TEST_SEED=<値> bun run test` で再現し、直す）。画面の検証は影響範囲に合わせて選ぶ（2026年10月8日、ユーザーより）。`bun run verify:webview -- --changed` は、まだ commit していない差分から下の2つのどちらかを選ぶ（`--dry-run` を付けると、選んだ範囲を表示するだけ）。
  - 水槽・展示室・生き物を足すなど、影響が特定の展示室に収まる変更は、`bun run verify:webview -- --halls=<展示室id>,...`（その展示室を 1440×960 と 420×912 で開き、広い画面では全水槽に出入りする。1室で約1分）。狭い画面で開くのは展示室の最初の水槽だけ。`--narrow-all` を付けると、狭い画面でも全水槽に出入りする（小さな生き物が見えるかを確かめるとき）。
  - 描画の共通部分、画面の配置、画面遷移・URL、読み込みの仕組み、館内図・図鑑など、設計が大きく変わる変更は、`bun run verify:webview`（全展示室・全水槽・図鑑・履歴。20分ほどかかる）。
- 描画の作りを変えたとき（体の変形を速くする、描き方を整理するなど）は、`bun run compare:render -- <前のビルド>` で絵が画素まで同じことを確かめ、`bun run measure:perf` で重さを比べる（[性能の計測と基準値](performance.md)）。測っている間は、テストやビルドを並行して走らせない（値が大きく出る）。
- **実機の Safari と iPhone での確認は要らない**（2026年10月10日、ユーザーより。効率が悪いので、基本的にやらない）。狭い画面は Bun.WebView の 420×912 で確かめれば足りる。「実機では確かめていない」を、やり残しとして毎回報告しなくてよい。
- 画面検証の実行中は、開発サーバーの再読み込みで結果が崩れるので、ソースを編集しない（文書の編集はよい）。
- ブラウザで見るときは localStorage を消してから見る（古い既定の匹数が残るため）。アプリ内のブラウザの枠が隠れていると描画が止まり、水槽が「10秒たっても準備が終わりません」になる。不具合ではないので、水槽の画面は枠を見える状態にするか、画面検証で確かめる。
- 展示計画・建物・展示室の枠・水槽の種を変えたら、`bun run plan:check` で計画とアプリの食い違いがないことを見る。
- 変更は検証のあと commit・push する。保管庫の変更も同様。
