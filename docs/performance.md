# 性能の計測と基準値

描画の重さを測る仕組みと、2026年10月10日の基準値、そこから分かったことをまとめる。種や水槽を足したあと、描画の作りを変えたあとに測り直し、悪化していないかを見る。

## 測り方

```bash
bun run measure:perf                        # 全展示室と水槽画面を測り、基準値と比べる（約7分）
bun run measure:perf -- --halls=amazon      # 展示室を絞る（その展示室と、その中のいちばん匹数の多い水槽）
bun run measure:perf -- --tanks=cube-30     # 指定した水槽の水槽画面だけを測る
bun run measure:perf -- --update-baseline   # 測った値を新しい基準値として保存する
bun run measure:perf -- --dist=<フォルダ>    # 別のビルドを測る（変更の前後を比べるとき）
```

`scripts/measure-performance.ts` が本番ビルド（`dist/`）を配り、`Bun.WebView`（WebKit）の狭い画面（420×912、画素比2）で次の2つを開いて測る。

- **展示室**: 全水槽を同時に描く画面。18室すべて。
- **水槽画面**: 各展示室でいちばん匹数の多い水槽。水中の光のフィルターがかかる。

基準値は `docs/performance-baseline.json`、直近の結果は `tmp/perf/latest.json` に入る。測っている間にテストやビルドを並行して走らせると、値が大きく出る。

測るのは Mac（M4 Pro）の上なので、iPhone での絶対値ではない。同じ Mac での前後の比較に使う。iPhone の実機では測っていない。

### 指標

| 指標 | 意味 |
|---|---|
| 計算 ms | 1フレームぶんの計算の量。描画と頂点の送信を空にして（GPU を待たないように）フレームを続けて進め、5回のうち最小を取る。測るたびの揺れが5%ほどと小さいので、**基準値との比較にはこれを使う**（15%と 0.1ms の両方を超えて増えたら知らせる）。内訳は、動き（シミュレーション）、体（メッシュの変形と配置）、描画（Pixi の描画命令の組み立て） |
| 実フレーム ms | 画面の更新（毎秒60回）に合わせたふだんの描画で、1フレームにメインスレッドでかかる時間の中央値。フレームの合間に CPU が休むので「計算」の数倍から20倍になり、測るたびに1〜2割揺れる。「遅い5%」は、遅いほうから5%のフレームの値 |
| GPU待ち ms | 描画命令を送ってから、GPU がそのフレームを描き終えるまで待った時間（1画素を読み戻して待つ）。何も描かなくても読み戻しだけで 1.2〜1.5ms かかるので、差を見る。Mac の GPU での値 |
| 描画回数、GL呼出 | 1フレームの描画（draw）の回数と、WebGL の呼び出しの総数 |
| 送信 KB、頂点 | 1フレームに GPU へ送り直す頂点などのデータの量と、変形するメッシュの頂点の数 |
| テクスチャ MB | GPU に載せているテクスチャの量（ミップマップを含む概算） |
| 画素 MP | キャンバスの画素数（百万画素）。見えていない部分も毎フレーム描く |
| 間隔 ms、遅い% | フレームの間隔の平均と、20ms を超えたフレームの割合（60fps なら 16.67ms、0%） |
| 表示 秒、読込 MB | 開き始めてから画面が見えるまでの時間と、その画面を直接開いたときに読むファイルの量 |

計算の時間を測るために、アプリに小さな窓口（`src/render/perfProbe.ts`）を置いている。計測スクリプトが sessionStorage に印を置いたときだけ働き、ふだんは何も記録しない。

フレームを間を置かずに続けて進めて「描画」の時間を測る方法は使わない。前のフレームの描画が GPU に残っているうちに次の頂点を送ると待たされ、実際にはない 1〜2ms が乗る（最初にこの方法で測り、描画が全体の7割を占めるように見えた）。

## 分かったこと

**1フレームの時間には大きな余裕がある。** 60fps の1フレームは 16.7ms。いちばん重い展示室（asia-oceania、176匹）でも、メインスレッドの計算は 0.8ms、ふだんの描画で 2.5ms（遅いフレームで 4.6ms）。計算の量は生き物の数にほぼ比例し、1匹あたり約 0.005ms。展示室1室の既定の匹数を180匹までにしている限り、種が1,300〜1,500に増えても1フレームの計算は増えない。

**体の変形はカエルだけが重かった（直した）。** カエルは脚の骨10本の回転の cos・sin を570あまりの頂点ごとに求め直していて、1匹が魚約50匹ぶんの重さだった。骨ごとに1度だけ求めるようにし、絵は1画素も変わらないことを確かめた。africa は 0.90ms から 0.51ms、キリフィッシュの小川水槽の体の変形は 0.20ms から 0.05ms になった。ほかの体のつくりでは、チンアナゴ（縦に64分割、1匹 0.017ms）とタツノオトシゴがやや重いが、問題になる量ではない。

**GPU の側は、生き物の数ではなくキャンバスの画素数で決まる。** GPU待ちは 20匹の展示室でも 176匹の展示室でも 2.0〜3.6ms で、読み戻しの固定の分（1.2〜1.5ms）を引くと、絵そのものは Mac の GPU で 1〜2ms。解像度を半分にすると約1ms 減った。狭い画面の展示室では、キャンバスが部屋の絵の全体（5.9 百万画素）で、見えているのはその4分の1（1.5 百万画素）。水槽画面は 1.5 百万画素でも、水中の光のフィルター（全画面のシェーダー）があるので GPU待ちは展示室と同じくらいになる。iPhone の GPU は M4 Pro より数倍遅いので、iPhone で重さが出るとすればここ。

**描画の回数は生き物の数と同じ。** 生き物1匹ごとに、頂点の送信1回と描画1回が出る（展示室で 44〜236 回、WebGL の呼び出しは 330〜1,770 回）。残りは水槽の窓と、手前の石・流木の切り抜き（ステンシル）。

**テクスチャは展示室1室で 33〜92MB。** 水景と部屋の絵が1枚 6MB（6水槽の展示室で 42MB）、生き物が1種あたり約 1.2MB（幅 720px、ミップマップつき）。展示室を移ると前の展示室の分を外す（`releaseTexturesExcept`）ので、館全体では積み上がらない。

**読み込みは画像が大半。** 展示室を直接開くと 2.2〜6.8MB で、うち画像以外（最初の JS 289KB、PixiJS 239KB、展示室の中身 60〜180KB、CSS、フォント、環境音など）が約 1.1MB、残りが画像。

**最初に読む JS（289KB、gzip 90KB）の7割は react-dom。** 内訳は react-dom 202KB、館の索引 17KB、App 17KB、react 8KB、設定パネル 7KB、館内図 7KB。水槽画面と設定パネルを展示室に入るときに読む形にしても、減るのは多くて 12KB（4%）なので、やらない。

**種のデータは1種あたり約 3.9KB。** 373種で 1.46MB（ecology 469KB、profile 446KB、catalog 393KB）。展示室の中身のチャンクには図鑑の解説（profile）も入っているが、チャンクは gzip で 50KB 以下で、同時に読む画像（数MB）に比べて小さい。図鑑の見出しは 181KB（1種 485バイト）で、1,500種なら約 730KB（gzip で約 150KB）。図鑑を開くときにだけ読む。

**リポジトリの画像は 125MB。** `src/content` のうち、生き物が 80MB（古い35種の原画 `side.png` が 53MB、全379の `body.webp` が 26MB で1種あたり約 70KB）、水景が 42MB（`plate.webp` が1枚あたり約 0.4MB）。`.git` のパックは 92MB。1,500種・200水槽になると、`body.webp` が約 105MB、水景が約 90MB の見込み。

**開発サーバーとテストの読み込みが遅かった原因は、内容のモジュールの監視の登録だった（直した）。** 内容のモジュール（`virtual:species/<id>` など）を1つ読むたびに、内容ファイル約1,100個すべてを監視に登録していた。373種を読むと11秒かかり、テストはファイルごとにこれを払っていた。モジュールが使うファイルだけを登録するようにして、1秒未満になった（ビルドの成果物は変わらない）。

## 試して、やめたこと

- **生き物のメッシュをまとめて描く（PixiJS の batch）**: 描画の回数は7割減った（asia-oceania で 236 → 69、WebGL の呼び出しは 1,770 → 500）。しかし頂点を CPU でまとめ直すぶん計算が 0.1〜0.16ms 増え、ふだんの描画のメインスレッドの時間は 5〜12% 増え、GPU待ちは変わらなかった（3回ずつ交互に測った）。絵は、縁の数百画素がわずかに違うだけだった。Mac では得にならないので入れていない。iPhone では WebGL の呼び出しが減るぶん得になるかもしれないが、実機で測らないと分からない。
- **水槽の窓の切り抜きを毎フレーム描き直さない**: 展示室は毎フレーム、水槽ごとに窓の四角を描き直している。大きさが変わったときだけにしても、測れる差が出なかったので戻した。

## まだやっていない、効きそうなこと

効果の見込みが大きい順。どれも、今の余裕の中では急がない。

1. **狭い画面の展示室で、見えている範囲だけを描く**: キャンバスの画素が4分の1になり、GPU の負荷が大きく減る。ただし今は、部屋の絵と同じ大きさのキャンバスをブラウザが横にスクロールしているので、指の動きに絵が遅れない。見えている範囲だけを描く形にすると、スクロールのたびに JavaScript で描き直すことになり、iPhone の慣性スクロールで絵が1フレーム遅れてずれるおそれがある。iPhone で展示室が重いと分かってから、実機で確かめながら進める。
2. **生き物の画像の大きさを、画面に出る大きさに合わせる**: 今はどの種も幅 720px。水槽に対して小さい種（水槽の幅の7%以下）は、いちばん寄っても 360px あれば足り、テクスチャが4分の1になる。半分の種が当てはまれば、展示室のテクスチャが2割ほど減る。画像の作り直し（`body.webp`）が要る。
3. **古い35種の原画 `side.png`（53MB）を保管庫へ移す**: アプリは `body.webp` しか読まない。原画は `scripts/build-fish-sprites.py` の入力で、新しい種の原画はすでに保管庫にある。移すとリポジトリの作業ツリーが4割軽くなる（履歴には残る）。
4. **react-dom を軽いものに替える**: 最初の JS が 289KB から 100KB 前後になる。画面の作りに関わるので、起動の遅さが問題になってから。
5. **シミュレーションの割り当てを減らす**: 回避領域の楕円を呼び出しのたびに作り直している（シミュレーションの時間の2割）。数値が変わらないようにキャッシュすれば、テストも速くなる。

iPhone の実機での値が要るときは、画面にフレームの時間を出す表示（URL で有効にする）を足して、実機で読む方法がある。

## 描画の作りを変えたとき: 絵が変わっていないことを確かめる

```bash
bun run build && cp -R dist tmp/dist-before          # 変更の前のビルドを取っておく
# （ソースを変更する）
bun run compare:render -- tmp/dist-before            # 変更の後と、全展示室で比べる（約10分）
bun run compare:render -- tmp/dist-before --halls=africa,amazon
```

`scripts/compare-render.ts` が、乱数と時刻を決まった値に差し替えたページで2つのビルドを同じフレーム数だけ進め、展示室のキャンバス全体を画素単位で比べる（読み込み直後、4秒後、14秒後）。同じビルドを2回動かして1画素も違わないことも、毎回確かめる。体の変形の計算を速くする、描き方を整理するなど、絵を変えないつもりの変更に使う。生き物の動きの計算を変えると位置が変わるので、全体が違って見える。
